# What I built

## 1. Role plumbing through NextAuth

`src/lib/auth.ts`:
- `authorize()` now returns `{ id, email, name, role }` (role pulled from
  `db.user.role`, falling back to `"user"`).
- `jwt({ token, user })` stashes `token.role = user.role ?? "user"` on first
  sign-in.
- `session({ session, token })` copies `token.role` onto `session.user.role`.

`src/lib/admin-guard.ts` (new):
- `requireAdmin()` — calls `getCurrentUser()`, then re-checks
  `db.user.findUnique({ select: { role: true } })`. Returns the session user
  if `role === "admin"`, else `null`.
- IMPORTANT: it always re-reads the DB. Do NOT trust `session.user.role` for
  authorization — a demoted admin's JWT still says "admin" until it rotates.
- `forbiddenResponse()` helper returns a 403 JSON response.

## 2. Admin API routes (all under `src/app/api/admin/`)

All seven routes share this access-control pattern:
```ts
const admin = await requireAdmin()
if (!admin) {
  const session = await getServerSession(authOptions)
  if (!session) return unauthorizedResponse()  // 401
  return forbiddenResponse()                    // 403
}
```

| Method + Path                              | Purpose                                                            |
|--------------------------------------------|--------------------------------------------------------------------|
| `GET  /api/admin/stats`                    | Platform totals (users/projects/websites/pages) + 7-day deltas     |
| `GET  /api/admin/users?limit&offset`       | Paginated users with `projectCount` (never selects `passwordHash`) |
| `PATCH /api/admin/users/[id]/role`         | `{ role: "user"\|"admin" }` — refuses self-role-change (400)       |
| `DELETE /api/admin/users/[id]`             | Cascade-deletes projects/websites/pages; refuses self-delete (400) |
| `GET  /api/admin/projects?limit&offset`    | Paginated projects with owner email + name                         |
| `DELETE /api/admin/projects/[id]`          | Admin override delete (no ownership check)                         |
| `POST /api/admin/bootstrap`                | One-shot: if zero admins exist, promotes current user; else 403    |

### Cascade behavior

User deletion cascades at the Prisma schema level (already configured):
```
User ← Project (onDelete: Cascade) ← Website (onDelete: Cascade) ← Page (onDelete: Cascade)
```
So `db.user.delete({ where: { id } })` removes the user's entire project tree
automatically. No manual cascade code needed.

### Self-protection

`PATCH /api/admin/users/[id]/role` and `DELETE /api/admin/users/[id]` both
compare `id === admin.id` and return HTTP 400 if true. This is enforced at the
API layer, not just in the UI.

### Bootstrap semantics

`POST /api/admin/bootstrap` is idempotent-safe:
- Counts admins: `db.user.count({ where: { role: "admin" } })`
- If `> 0` → 403 (bootstrap permanently disabled after first admin)
- If `=== 0` → promotes current user, returns the new admin row

The worst-case race (two simultaneous bootstrap calls when no admin exists)
could create two admins. Acceptable for the deployment-time one-shot path.

# Notes / caveats

1. **JWT role staleness.** When you promote/demote a user via the admin API,
   their existing JWT still carries the old role until it rotates. This is
   why `requireAdmin()` always re-reads the DB. Client-side code that reads
   `session.user.role` (like the sidebar's "Super Admin" link) will only
   update after the user re-signs-in or the token refreshes. This is
   acceptable for UI affordances but never for authorization.

2. **Bootstrap race.** Two simultaneous bootstrap calls when no admin exists
   could both pass the `count === 0` check and create two admins. Not worth
   a transaction for a deployment-time one-shot path.

3. **Pagination is simple limit/offset.** No cursor pagination. Fine for
   admin tables expected to stay in the thousands; revisit if the user table
   grows beyond ~10k rows.
